# 平台文件中心（File Center）架构设计方案

> 版本：v0.1（评审稿）
> 日期：2026-08-17
> 状态：待评审

---

## 一、背景与目标

### 1.1 背景
平台已集成 `third_party/<tool_name>/` 下的多类第三方工具（A 类后端工具、B 类 AI/RAG 工具、C 类纯前端）。各工具普遍存在文件操作诉求：上传、读取、报告导出等。早期方案设想"为每个平台改造其文件上传/读取/导出接口以对接统一文件中心"，但存在致命问题：

- 第三方工具代码不属于我们，多数难以改造；
- 各工具文件接口五花八门，逐一写适配器工作量巨大且脆弱；
- 并非所有工具都需要文件管理能力。

### 1.2 核心目标
1. 建立**平台级文件资产中心**：统一 上传 / 删除 / 建分类 / 归档 / 管理，文件真实落盘于服务器并按工具隔离。
2. **每个工具在自己隔离的文件夹下**，用户在工具内部即可 树形浏览 / 精确定点勾选单个文件 / 选定后在本工具内开始处理。
3. **避免为所有工具强制改造文件接口**——只有"需要与平台共享文件资产"的工具才接入，且通过挂载卷/复用组件实现低侵入接入。

### 1.3 设计原则
- **文件中心只管文件资产**，不做"替所有工具实现对文件的业务调用"。
- **namespace（工具标识）作为隔离与权限的边界**。
- **物理按分类建文件夹 + 逻辑标签/归档**：分类对应真实 Linux 文件夹，标签/归档/所有者仅存数据库。
- **复用优先**：选文件能力做成可复用 iframe 组件，第三方 dist 也能一键接入。

## 二、架构分层

```
┌────────────────────────────────────────────────────────────────┐
│            平台层 · 文件中心（File Center）                      │
│   全局管理视图：上传 / 删除 / 建分类 / 归档 / 管理               │
│   对接接口：upload / list / download / delete / category        │
└───────────────────────────┬────────────────────────────────────┘
                            │ 同一份物理磁盘，不同视图
┌───────────────────────────▼────────────────────────────────────┐
│          工具层 · 工具内部文件选择（FilePicker）                │
│   namespace 隔离的文件树 + 复选框精确定点勾选 + 工具内处理       │
│   复用形态：iframe 页面（?ns=<tool>）或 npm 组件                │
└────────────────────────────────────────────────────────────────┘
```

**两份视图同源**：平台文件中心（全局管理）与工具内 FilePicker（namespace 选择）指向同一份物理文件，只是入口与权限视图不同。

## 三、物理目录模型

### 3.1 物理结构
```
<data_root>/<一级分组>/<功能型>/<工具 namespace>/<原文件名>
```

- `<data_root>`：平台统一的文件存储根。**容器内为 `/data/files`，对应宿主 `/opt/aixsilicon/files`**（经卷挂载打通，见 §3.3）。
- `<一级分组>`：业务分组，固定八组：器件组、GaN功率组、系统与表征组、外延组、sic开发组、射频组、工艺工程组、si基研发组。
- `<功能型>`：工具功能类型，每组下固定三类：**数据处理**（数据处理的程序/工具）、**报告产出**（PPT报告制作程序/工具）、**原始数据**（数据库相关程序/工具）。
- `<工具 namespace>`：具体工具标识（如 `cp_report`、`rag`），**最底层，每个工具独立目录，天然隔离**。
- `<原文件名>`：物理文件**保留用户原始文件名**（如 `2026_Q3.xlsx`），不重命名；系统另分配唯一 `id`（UUID）存数据库作为标识主键，二者一一对应。

> **命名约定**：物理落盘不改变用户上传的文件名，仅用 DB 中的唯一 `id` 精确定位。同名冲突由 `id` 区分（同一目录下若重名，可追加短后缀或提示重命名，展示名仍为原文件名）。

> 与既有约定对齐：A 类工具自管 `third_party/<tool>/data/`。平台文件中心将其工具空间作为该工具共享/归档目录，工具自身的运行数据（模型/DB/日志等私有数据，如 `/opt/rag/`）**不并入文件中心**，保持各自 `/opt/<tool>/` 独立；工具如需读取文件中心共享资产，仅挂载共享路径。

**八个一级分组：**
器件组 · GaN功率组 · 系统与表征组 · 外延组 · sic开发组 · 射频组 · 工艺工程组 · si基研发组

**每个一级分组下的三个功能型：**
数据处理 · 报告产出 · 原始数据

**目录示例（容器内视角，对应宿主 `/opt/aixsilicon/files/`）：**
```
/data/files/器件组/数据处理/晶体管参数提取/2026_Q3.csv
/data/files/GaN功率组/报告产出/功率报告生成/report.pptx
/data/files/sic开发组/原始数据/器件样品库/sample_list.xlsx
/data/files/射频组/数据处理/射频参数扫描/scan_result.json
```

### 3.3 容器化部署与数据根（生产）
- **宿主数据根**：`/opt/aixsilicon/files/`（绝对路径，与既有 `/opt/rag/` 风格一致）。
- **容器内路径**：`/data/files`（api 进程读写）。
- **docker-compose.yml** 在 `api` 服务增加卷映射：
  ```yaml
  api:
    volumes:
      - ./services/aixsilicon-api:/app
      - /opt/aixsilicon/files:/data/files    # 文件中心数据根
  ```
- **`DATA_ROOT`** 配置为容器内 `/data/files`。
- **初始化目录（一次性，宿主执行）**：
  ```bash
  bash scripts/create_file_center_dirs.sh /opt/aixsilicon/files
  ```
  该脚本在宿主上按绝对根创建 8×3=24 个分类文件夹；工具最底层目录在工具注册时由后端按 `分组/功能型/工具` 自动补齐。

### 3.4 一键建目录脚本
- 脚本：`scripts/create_file_center_dirs.sh`
- 逻辑：遍历 8 组 × 3 型，对每个组合 `mkdir -p`；根目录可用参数/环境变量覆盖。
- 已用组合校验确认：8×3 = **24 个目录**，与八组三型完全对应。
### 3.2 分组/分类建目录约定
- **一级分组、功能型、工具均为 Linux 真实文件夹**，逐层创建（工具注册/启用时按 `一级分组/功能型` 自动建目录）。
- **标签、归档、所有者等仅存数据库**，不反应在路径上（一个文件可有多个标签；归档为软删物理保留）。
- 重命名 / 移动分组/工具时：后端**同步移动**对应物理文件夹及其下文件（涉及文件较多时前端二次确认并留痕）。

## 四、数据库模型

### 4.1 `file_assets` 文件资产表
| 字段 | 类型 | 说明 |
|------|------|------|
| id | UUID PK | 文件唯一标识（逻辑主键，用于接口定位/勾选）|
| group_name | String(50) index | 一级分组（器件组/GaN功率组/…八组之一） |
| func_type | String(50) index | 功能型（数据处理/报告产出/原始数据） |
| namespace | String(50) index | 工具标识，隔离边界（最底层工具目录） |
| filename | String(255) | 原始文件名（物理落盘名，展示用） |
| ext | String(20) | 扩展名 |
| size | BigInteger | 字节数 |
| mime | String(100) | MIME 类型 |
| storage_path | String(500) | 相对 `<data_root>` 的物理路径 |
| category_id | FK categories | 所属分类（与物理文件夹一致，可空=根目录） |
| tags | JSON | 标签列表 |
| is_archived | Boolean | 是否归档 |
| owner_id | FK users | 上传者 |
| created_at | DateTime | |
| updated_at | DateTime | |

### 4.2 `file_assets` 与 `tools` 的关系
- 不强加外键绑定（第三方工具可能动态注册），`namespace`（工具）+ `group_name` + `func_type` 作为逻辑关联。
- 平台"工具管理"可为每个工具登记：所属 `group_name`（八组之一）、`func_type`（数据处理/报告产出/原始数据）、可选 `file_scope`，见 §八。

## 五、后端接口清单（`/api/v1/files`）

统一鉴权：需登录；按 `group_name / func_type / namespace` 组合路径做权限边界校验。追加白名单、大小限制、路径穿越校验（拦截 `..`、绝对路径、特殊字符）。工具空间路径由 `group_name/func_type/namespace` 推导。

| 方法与路径 | 说明 |
|-----------|------|
| `POST /api/v1/files/upload` | 上传，`multipart`，参数 `group_name` + `func_type` + `namespace`(工具) + 文件 |
| `GET /api/v1/files?group_name=X&func_type=Y&namespace=Z&keyword=...` | 文件清单（分页、过滤），返回元数据 |
| `GET /api/v1/files/tree?group_name=X&func_type=Y&namespace=Z` | 返回 分组→功能型→工具→文件 树形结构，供 FilePicker 浏览 |
| `GET /api/v1/divisions` | 返回八组 × 三型 目录结构（供前端侧边栏/树） |
| `GET /api/v1/files/{id}/download` | 下载文件内容 |
| `GET /api/v1/files/{id}/content` | 读取文件内容（文本/JSON，供工具直接消费） |
| `DELETE /api/v1/files/{id}` | 删除物理文件 + 元数据 |
| `PATCH /api/v1/files/{id}` | 重命名、移动分组/功能型/分类、加标签、归档/取消 |
| `POST /api/v1/files/{id}/archive` | 归档（软删，物理保留） |
| `POST /api/v1/files/upload/multi` | 批量上传 |
| 复用既有 `/api/v1/categories` | 一级分组/功能型可作为平台分类树维护 |

> 工具内选文件后"处理文件"的数据流有两种（二选一或都支持）：
> - **绝对路径注入**（默认推荐）：共享挂载卷的 A/B 类容器直接读文件系统路径，零拷贝、性能最好；文件中心返回 `storage_path` 绝对路径。
> - **内容读取**：跨容器/非挂载场景用 `GET /content/{id}`。

## 六、前端页面

### 6.1 平台文件中心页面（路由 `/files`）
- 全局管理视图，左侧 **八组×三型→工具** 树，右侧文件列表。
- 能力：上传、批量上传、预览、下载、重命名、删除、移动分组/功能型、打标签、归档、搜索过滤。
- 权限：管理员全量；普通用户可按授权分组/工具查看管理。

前端新增 `src/pages/FileCenter/` 目录，路由注册于 `src/routes/index.tsx`。

### 6.2 FilePicker 组件（复用核心）
- **形态：独立 iframe 页面** `GET /tools/file-picker/?group=<八组>&func=<型>&ns=<工具>&multi=true`，任何 C 类纯前端工具用 `<iframe>` 或 `window.open` 接入，**零 npm 依赖**。
- 能力：树形浏览该工具空间文件 → 复选框精确定点勾选 → 通过 `postMessage` 回报选中的文件 id / 绝对路径列表给宿主工具。
- 另提供 React npm 组件封装（`FilePicker.tsx`）供平台原生工具直接内嵌。

## 七、与第三方工具的接入方式（关键：低侵入）

| 工具类型 | 是否需文件能力 | 接入方式 | 服务端改造量 |
|---------|--------------|---------|-------------|
| **原生工具**（前后端在主项目） | 建议接入 | 直接用文件中心 API + React FilePicker 组件 | 中（但代码自研可控） |
| **A 类后端工具**（第三方容器） | 可选：共享/归档空间 | 容器挂载 `${data_root}/<分组>/<功能型>/<工具>` 卷，读取绝对路径；前端嵌 iframe FilePicker | 极低（改配置，不动业务代码） |
| **B 类 AI/RAG 工具** | 推荐：知识库/素材 | 设 `RAG_DATA_DIR` 指向挂载的 `${data_root}/<分组>/<功能型>/<工具>`，**零代码** | 极低（环境变量） |
| **C 类纯前端** | 视需求 | 前端 iframe 嵌 FilePicker + 调文件中心 API 做上传/导出 | 需改它的上传/导出 JS（仅需要的工具） |

**核心结论：只有"需要与平台共享同一份文件资产"的工具才需改造，且多数通过挂载卷 / 复用组件低侵入实现，不必为所有工具改文件接口。**

## 八、权限模型（第一阶段收敛）

- **按分组+工具隔离**（第一优先级）：工具 A 用户仅见 A 工具空间（`分组/功能型/工具`）文件。工具内勾选接口强制校验当前工具空间。
- **工具内文件全可见**（第一阶段不做文件级权限下钻），避免过度设计。
- 管理员拥有全平台文件管理权限。
- 鉴权实现：接口统一校验"当前用户 → 工具（含分组/功能型）"映射（复用既有权限体系 `button:tools:use` 等）。

### 工具登记增强（可选，写进 INTEGRATION_STANDARD）
tools.config 增加可选字段：
```json
{
  "file_scope": "share" | "picker" | "managed" | "none"
}
```
- `none`：不需要文件能力（默认）
- `picker`：工具内嵌 FilePicker 选择
- `share`：挂载卷共享数据目录
- `managed`：完全托管文件读写（仅原生/战略工具）

## 九、安全要点
- 上传白名单扩展名/大小限制；路径穿越校验（`..`、绝对路径、`\`/`/` 非法字符）。
- 物理保留原文件名：上传时对文件名做净化（去路径、去危险字符），防止目录遍历与特殊字符注入。
- 下载/读取接口做分组+工具空间权限校验，防止跨工具越权。
- 归档为软删，防止误删；真正的物理删除需二次确认。

## 附：设计决策对照（C 方案）

| 决策点 | 采用方案 |
|--------|---------|
| 物理结构 | `data_root/<八组>/<三型>/<工具>/<原文件名>` 按分组建真实文件夹；唯一 id 存 DB |
| 命名 | 物理保留原文件名，`id`(UUID) 作为标识主键 |
| 分组 | 八个一级分组(器件组/GaN功率组/…) × 三个功能型(数据处理/报告产出/原始数据) |
| 分类/归档 | 分组/工具=Linux 真实文件夹；标签/归档仅存 DB，不动物理 |
| 工具内选文件 | 工具空间(分组/功能型/工具)文件树 + 复选框 + 绝对路径返回 |
| 权限第一阶段 | 仅分组+工具隔离，内部全可见 |
| 数据根(容器化) | 宿主 `/opt/aixsilicon/files` ↔ 容器 `/data/files` 卷挂载；工具私有数据(`/opt/<tool>`)不并入 |
| FilePicker 复用 | 独立 iframe 页面，`?group=&func=&ns=` 传参 + postMessage |
